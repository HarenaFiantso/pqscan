Why

You can't migrate
what you can't find.

A large enough quantum computer running Shor's algorithm would break RSA, ECDSA, EdDSA, ECDH, DH and DSA. pqscan shows where that cryptography is, and how urgently each use needs to be replaced.

Today
2030NIST plans to deprecate these algorithms after this year.
2035NIST plans to disallow them after this year.

Dates from NIST IR 8547. The replacements are ML-KEM for key exchange and ML-DSA for signatures.

Mosca's theorem

Data can be recorded today and decrypted later, so the deadline isn't the day a quantum computer exists. If X + Y > Q, some of your data will still need protecting after it can be broken. Nobody knows Q, so the numbers are yours to choose.

pqscan uses it to rank findings: give it X and Y for each part of your code in a project file.

Install

Install it.
Point it at your code.

Each release has an archive for Linux on x86-64 and arm64, and for macOS on Apple silicon, with the binary, its man page and a SHA256SUMS file. The Linux binary is fully static, so it runs on any distribution. The macOS one needs macOS 15 or newer.

shell
version=1.0.0 platform=linux-x86_64   # or linux-aarch64, macos-arm64
base=https://github.com/HarenaFiantso/pqscan/releases/download/v$version
curl -fL -O "$base/pqscan-$version-$platform.tar.gz" -O "$base/SHA256SUMS"
sha256sum --check --ignore-missing SHA256SUMS
tar -xzf "pqscan-$version-$platform.tar.gz"
sudo cp -R "pqscan-$version-$platform/." /usr/local/

Every archive is attested by the workflow that built it: gh attestation verify checks it, as the README shows.

shell
docker run --rm -v "$PWD:/src:ro" ghcr.io/harenafiantso/pqscan:1
docker run --rm -v "$PWD:/src:ro" ghcr.io/harenafiantso/pqscan:1 --format sarif . > pqscan.sarif

The image holds the static binary and nothing else, for x86-64 and arm64, and runs as nobody. Options replace the default path, so name . after them.

shell
cmake --preset release -DPQSCAN_BUILD_TESTS=OFF
cmake --build --preset release
sudo cmake --install build/release

You need CMake 3.20 or newer, a C11 compiler and OpenSSL 3.0 or newer with its headers. CMake downloads the other dependencies, pinned by hash.

Usage

shell
pqscan [OPTIONS] PATH...

Each PATH is a file or a directory. Directories are walked recursively and symlinks are never followed. pqscan reads four kinds of files, and skips every other file. The first three are chosen by name. ELF files are recognized by their first four bytes, whatever their name. man pqscan has it all, once installed.

C and C++ source

.c, .h, .cpp, .hpp, .cc, .cxx, .C, .hh, .hxx, .ipp, .inl and .tcc

Configuration

.conf, .cnf, sshd_config, ssh_config, .htaccess, and any file in a sites-available or sites-enabled directory

Certificates and keys

.pem, .crt, .cer, .der, .key and .csr

ELF binaries

64-bit executables, shared libraries and object files

OptionMeaning
-i, --ignore PATTERNSkip paths matching a glob, tried on the file name, the path, and the path relative to PATH. Repeatable. .git is always skipped.
-r, --rules FILEUse the rules in this JSON file instead of the built-in ones.
--project FILERead how long data must stay secret from this project file. The default is .pqscan.json in the current directory, if there is one.
--as-of YEARScore priorities as if it were this year. The default is the current year, in UTC.
-f, --format FORMATWrite the report as text (the default), json, cbom or sarif.
--fail-on LEVELThe lowest risk level that makes pqscan exit 1. The default is REVIEW. Every finding is still reported.
--diff FILEReport only the findings this baseline does not accept.
--write-baseline FILEWrite a baseline that accepts every finding to this file, and report as usual.
--max-time SECSStart on no new file after this long. The default is 3600. Files left over are skipped, so the scan is incomplete.

-V, --versionShow the version and exit.

Detection

It reads syntax.
Not text.

pqscan parses each file with Tree-sitter, so a comment that mentions RSA is not a finding, and broken code is still scanned.

Reported

Calls and other uses of known identifiers, including in macro bodies and in every branch of #ifdef, plus algorithm names passed to known calls, such as "RSA" in EVP_PKEY_CTX_new_from_name.

Reported only when called

MD5 and SHA1, since those names are also common enum values and variables.

Not reported

Comments, other strings, declarations such as prototypes, struct fields, C++ methods, and code under a literal #if 0.

It follows constants.
And never guesses.

pqscan resolves values inside one file: locals in order, #defines, const and constexpr globals, strings, and +, -, * and << on constants. What it can't prove stays unknown.

keys.c
#define KEY_BITS 4096
static const int DOUBLE_BITS = 2048 * 2;

void make(RSA *r, int size) {
    RSA_generate_key_ex(r, KEY_BITS, NULL, NULL);
    RSA_generate_key_ex(r, DOUBLE_BITS, NULL, NULL);
    int bits = KEY_BITS;
    RSA_generate_key_ex(r, bits, NULL, NULL);
    RSA_generate_key_ex(r, 1 << 12, NULL, NULL);
    RSA_generate_key_ex(r, size, NULL, NULL);
}
  • KEY_BITSRSA-4096
  • 2048 * 2RSA-4096
  • bits = KEY_BITSRSA-4096
  • 1 << 12RSA-4096
  • a parameterRSA-unknown
What stays unknown
  • Anything from another file, a parameter, or a global that isn't constant.
  • A variable written in a branch, from that write on, or in a loop, from the start of the loop.
  • A variable changed by += or ++, or whose address is taken. In C++, also one passed to a call or bound to a reference, since the call could change it.
  • A macro with parameters, named by #undef, defined twice differently, or defined inside #if or #ifdef, other than a header's include guard. That includes #ifndef BITS defaults, which the build can override.
  • Enum constants, which aren't followed yet.

Configs, certificates, keys and binaries

TLS and SSH settings

Cipher strings, groups and signature algorithms in openssl.cnf, nginx and Apache, and OpenSSH's KexAlgorithms, HostKeyAlgorithms, Ciphers and MACs. ECDHE-RSA-AES128-GCM-SHA256 reports ECDH, RSA and AES-128.

Certificates and keys

PEM or DER, decoded by OpenSSL's libcrypto: the key and its size, what the key usage says it does, the signature and its digest, and when the certificate expires. Each PEM block names its own line.

ELF binaries

The symbol tables of 64-bit executables, libraries and object files, read by a bounds-checked reader that is fuzzed in CI. A function a binary imports or contains, such as RSA_sign, is reported for the whole file.

Not reported

Names a setting takes away, such as !RSA or -ssh-rsa, and hybrid post-quantum groups such as X25519MLKEM768. Aliases such as DEFAULT or HIGH aren't expanded, since their meaning depends on the OpenSSL build.

Where one name stands for two weaknesses, pqscan reports the more severe: ssh-rsa signs with SHA-1, so it's SHA-1. An encrypted PKCS#8 key hides its algorithm, so its file isn't analyzed, and pqscan never asks for a passphrase. Neither is a stripped static executable, which keeps no symbols to read.

Risk

Four levels.
One verdict per finding.

A finding has exactly one level, the most severe that applies. That's why RSA-1024 is CLASSICALLY_WEAK, not QUANTUM_VULNERABLE: it's already unsafe today.

  1. CLASSICALLY_WEAK

    Already unsafe today: MD5, SHA-1, DES, 3DES, RC4, and RSA, DSA or DH under 2048 bits.

  2. QUANTUM_VULNERABLE

    Broken by Shor's algorithm, so they must migrate: RSA, ECDSA, EdDSA, ECDH, DH and DSA.

  3. REVIEW

    Weakened by Grover's algorithm: AES-128 and other symmetric algorithms.

  4. OK

    AES-256, SHA-256 and stronger, ML-KEM, ML-DSA, SLH-DSA. The built-in rules don't report these, but your own rules can.

Severity order, used by --fail-on: OK < REVIEW < QUANTUM_VULNERABLE < CLASSICALLY_WEAK. An unknown key size keeps the algorithm's usual level, because guessing would hide or invent a weakness.

From level to priority

Every finding also gets a priority from 0 to 100, and reports list the most urgent first. What is broken today scores 100, REVIEW 10 and OK 0. A QUANTUM_VULNERABLE finding scores from 50 to 99, as the sum of:

PointsFor
50Being breakable by Shor's algorithm at all.
10 or 20NIST IR 8547 deprecating the algorithm, after 2030, or disallowing it, after 2035, in the year the migration would end.
0 to 29Mosca's 10 + X + Y − Q, kept in that range. It is over 10 exactly when the data is exposed, and every year of exposure adds a point.

Q runs from --as-of, the current year by default, to the quantum year, 2035 unless you say otherwise: the year IR 8547 disallows these algorithms, a planning date rather than a forecast. Without a project file X and Y are 0, so the dates alone decide. With one, each part of the code gets its own:

.pqscan.json
{
  "schema_version": 1,
  "quantum_year": 2035,
  "secrecy_years": 0,
  "migration_years": 3,
  "components": [
    {"name": "payments", "paths": ["src/payments/*", "*.pem"], "secrecy_years": 25, "migration_years": 7},
    {"name": "telemetry", "paths": ["src/telemetry/*"], "secrecy_years": 1}
  ]
}

The first component with a matching glob wins, and a path no component claims gets the top-level years. Patterns match paths as the report prints them, so run pqscan from the project root, where it reads .pqscan.json. A project file only reorders findings: it never hides one or changes the exit code.

Reports

One scan.
Four formats.

--format picks what goes to stdout. Warnings always go to stderr, so a report can be redirected to a file as it is. The same files, rules, project file and --as-of year give the same bytes: reports hold no timestamp and no random identifier.

For reading in a terminal. One line per finding, most urgent first, then a count. A clean scan prints nothing.

report/mixed.c:4: RSA-1024 (CLASSICALLY_WEAK, priority 100)
report/mixed.c:11: RC4 (CLASSICALLY_WEAK, priority 100)
report/mixed.c:12: MD5 (CLASSICALLY_WEAK, priority 100)
report/mixed.c:3: RSA-2048 (QUANTUM_VULNERABLE, priority 51)
...
10 findings: 3 CLASSICALLY_WEAK, 6 QUANTUM_VULNERABLE, 1 REVIEW

File names are untrusted input: control characters, bidirectional marks and invalid UTF-8 print as \xNN, and a backslash prints doubled.

For scripts. key_size is a number, "unknown" when pqscan can't prove it, or null when the algorithm has no key size. line is null for a finding about a whole file, such as a DER certificate, and expires is when a certificate stops being valid. priority shows how the finding was scored.

For code scanning services, as SARIF 2.1.0. Each algorithm is one rule. CLASSICALLY_WEAK and QUANTUM_VULNERABLE are errors, REVIEW is a warning and OK is a note. A result's rank is its priority.

{
  "ruleId": "pqscan/RSA",
  "level": "error",
  "rank": 51,
  "message": {
    "text": "RSA_generate_key_ex uses RSA-2048: QUANTUM_VULNERABLE"
  },
  "locations": [
    {
      "physicalLocation": {
        "artifactLocation": {
          "uri": "report/mixed.c"
        },
        "region": {
          "startLine": 3
        }
      }
    }
  ]
}

Paths are URIs: bytes that aren't plain in a URI are percent-encoded, and a leading ./ is dropped so that code scanning can match them to the repository.

A partial report can't pass for a whole one

Paths that can't be read are skipped with a warning, as are files over 64 MiB, source and configuration files that contain a NUL byte, source files that take more than 30 seconds to parse, encrypted PKCS#8 keys, certificate or key files that can't be decoded, and ELF files that are 32-bit, damaged, or have no symbol table. CI

Exit codes
a pipeline can trust.

--fail-on sets the lowest level that fails a run. It changes only the exit code, so every finding is still reported. The panel starts with the ten findings from the run above.

--fail-on
Findings at each level

exit1

Exit codeMeaning
0No findings at or above --fail-on, and everything in scope was analyzed
1Findings at or above --fail-on, even if the scan was incomplete. With --diff, only new findings count, and with --write-baseline, none do
2Usage error, such as a path that doesn't exist or a rule, project or baseline file that isn't valid
3Internal error
4No findings at or above --fail-on, but something in scope could not be analyzed
shell
pqscan --fail-on CLASSICALLY_WEAK src        # fail only on what is unsafe today
pqscan --format sarif src > pqscan.sarif     # for code scanning
pqscan --format cbom src > pqscan.cdx.json   # for an inventory
pqscan --format json src | jq .summary.by_risk

Block new findings. Accept the old ones.

A baseline lists the findings a project accepts today, and --diff reports only the others. An entry names a finding by its path, algorithm, symbol, primitive and key size, with a count. The line isn't part of it, so editing code above a finding doesn't make it new, but a third identical call in a file that had two does. Entries no finding used any more are counted on stderr, so that a stale entry can't quietly accept the same call if it comes back.

shell
pqscan --write-baseline .pqscan-baseline.json .   # accept what is there now, and commit it
pqscan --diff .pqscan-baseline.json .             # exits 1 only on new findings

The GitHub Action builds pqscan, uploads every finding to code scanning, and fails the job only on findings the baseline doesn't accept. Code scanning still sees the accepted ones, so their alerts stay open.

yaml
permissions:
  contents: read
  security-events: write

jobs:
  pqscan:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
      - uses: HarenaFiantso/pqscan@v1
        with:
          baseline: .pqscan-baseline.json

@v1 follows every 1.x release. A pull request can edit the baseline it's checked against, so the README shows a gate that reads it from the base branch instead, and how to pin the action to a commit.

Exit code 0 doesn't prove the code is free of vulnerable cryptography. pqscan only recognizes the names in its rules, in the kinds of files it reads.

Rules

Bring your own rules.

The built-in rules live in rules/default.json and are compiled into the binary. --rules FILE replaces them with a file of the same format. An install puts a copy in share/pqscan/default.json to start from.

rules.json
{
  "schema_version": 1,
  "algorithms": [
    {"name": "RSA", "risk": "QUANTUM_VULNERABLE", "weak_below_bits": 2048},
    {"name": "MD5", "risk": "CLASSICALLY_WEAK"}
  ],
  "rules": [
    {"pattern": "RSA_sign", "kind": "function", "algorithm": "RSA", "primitive": "signature"},
    {"pattern": "EVP_PKEY_RSA", "kind": "constant", "algorithm": "RSA", "primitive": "unspecified"},
    {"pattern": "MD5", "kind": "function", "algorithm": "MD5", "primitive": "hash", "call_only": true},
    {"pattern": "RSA", "kind": "string", "algorithm": "RSA", "primitive": "unspecified"},
    {"pattern": "ffdhe2048", "kind": "config", "algorithm": "DH", "primitive": "key_exchange", "key_bits": 2048},
    {"pattern": "rsaEncryption", "kind": "key", "algorithm": "RSA", "primitive": "unspecified"}
  ],
  "calls": [
    {"name": "RSA_generate_key_ex", "key_bits_argument": 1},
    {"name": "EVP_PKEY_CTX_new_from_name", "algorithm_argument": 1}
  ]
}
SectionFieldMeaning
algorithmsnameThe normalized name shown in reports.
riskOK, REVIEW, QUANTUM_VULNERABLE or CLASSICALLY_WEAK.
weak_below_bitsOptional. Shorter keys are CLASSICALLY_WEAK.
rulespatternThe identifier, string or name to find.
kindfunction, constant or macro for source identifiers, string for an algorithm name passed to a call, config for a name in a TLS or SSH setting, or key for OpenSSL's short name of a key or digest type.
algorithmA name declared in algorithms.
primitivesignature, key_exchange, encryption, hash or unspecified.
call_onlyOptional, for functions. Count the name only when it's called.
key_bitsOptional, for config, function, constant and macro rules. The key size the name itself fixes, as in ffdhe2048 or NID_secp384r1.
callsnameA function whose arguments are worth reading.
key_bits_argumentOptional. Position of the key size, from 0.
algorithm_argumentOptional. Position of a string naming an algorithm, from 0.

A string pattern only counts as an argument of a call listed in calls. string, config and key patterns ignore case, and each kind has its own names. pqscan refuses the whole file on any mistake, such as an unknown field, and names the entry at fault. CONTRIBUTING.md explains how to add a built-in rule.

Inside

Scanners produce.
Reporters consume.

Scanners produce finding structs and reporters consume them, and neither knows about the other. Adding an input type or an output format never requires changes elsewhere.

  1. walk

    Sorted directory walk, ignore patterns, file types.

  2. scan

    Syntax tree, rules, constant flow, configs, certificates, ELF.

  3. findings

    Path, line, symbol, algorithm, key size, primitive, risk, priority.

  4. report

    text, json, cbom or sarif, written as a stream.

Built for hostile input

pqscan reads untrusted repositories. It never runs what it scans, every parse has a time budget, and a crafted file name can't forge a report line or break a JSON document.

Plain, strict C11

POSIX, no compiler extensions, zero warnings under strict flags. Every test passes under ASan, UBSan and Valgrind, on GCC and Clang, on Linux and macOS, and against musl.

Checked against the specs

CI validates CBOM and SARIF output against the official CycloneDX and SARIF schemas, including on file names built to break them.

Measured, not claimed

On hand-labeled code from OpenSSH, curl, nginx, Mosquitto, HAProxy and PostgreSQL, pqscan finds 98.6% of the OpenSSL uses it was never tuned on, with no false positive.

Fuzzed, every parser

Each parser of untrusted input, from the ELF reader to the JSON loaders, has a libFuzzer target that checks its output too. CI runs them on every change, and for half an hour every night.

Fast enough for every pull request

About 5 MiB of C per second on one core. The whole OpenSSL source tree takes under 6 seconds and 38 MiB of memory, and CI fails if that slips.
